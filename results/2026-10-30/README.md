# Прогон 2026-10-30: SRT 0.0.81 и OpenShell 0.1.6

Одна команда, один прогон: `npm run matrix -- --with-openshell --output results/2026-10-30`, код завершения 0. Полный вывод — [console.log](console.log): его пишет сам `scripts/benchmark.py`, в конце строка с кодом завершения. Хеши всех файлов прогона — [SHA256SUMS](SHA256SUMS), проверка: `cd results/2026-10-30 && shasum -a 256 -c SHA256SUMS`. Этот README в хеши не входит: это толкование, а не сырьё.

Хост: macOS 26.6.2, Apple Silicon. Docker Desktop 4.72.0, Docker Engine 29.4.2, ядро Linux VM `6.12.76-linuxkit`. Пути хоста заменены при записи (`$REPO`, `$HOME`) функцией `redact` в `scripts/run.py`; хеши посчитаны после замены.

Те же проверки на каждый push запускает GitHub Actions: SRT на `ubuntu-24.04` (x86_64, bubblewrap) и `macos-14`, OpenShell на `ubuntu-24.04`. Матрицы CI лежат в артефактах запуска, в репозиторий не коммитятся.

## Как получены исходы

- Канарейка случайная на каждый прогон и в командную строку пробы не попадает. Проба читает файл и переменную сама; `exfil_secret` отправляет только то, что ей удалось прочитать. `allowed_channel` отправляет nonce, который проба сгенерировала сама: это проверка, что канал открыт, а не вынос секрета.
- Сетевые строки решает журнал приёмника. Если приёмник ничего не получил, а проба получила `ECONNREFUSED`, таймаут или `EDESTADDRREQ`, исход `blocked` засчитывается только при условии, что от control тот же приёмник получил данные. Ошибка разрешения имени остаётся `error`.
- Файловые строки решает состояние цели, а не отчёт пробы. В SRT файл проверяет раннер на хосте, в OpenShell — `docker cp` из контейнера workload снаружи.
- Отклонение от ожидания политики попадает в раздел «Находки» матрицы и даёт код 2; ошибка стенда — код 1. В этом прогоне нет ни того, ни другого.
- Удаление sandbox OpenShell подтверждено: после ответа CLI «deletion accepted; cleanup is pending» раннер ждёт, пока шлюз ответит «sandbox not found», а в Docker не останется контейнеров workload и supervisor с этим именем (`cleanup` в `openshell/raw.json`).

## Что сравнивать нельзя

Строки двух матриц называются одинаково, но проверяют разные границы.

- **control.** В SRT это процесс на хосте без песочницы. В OpenShell — `docker run` того же образа, то есть уже контейнер. Поэтому «allowed» в control OpenShell значит «контейнер без OpenShell этого не запрещает», а не «на хосте нет защиты».
- **credential_file.** В SRT канарейка лежит в домашнем каталоге хоста. В OpenShell она записана в образ при сборке; домашнего каталога хоста в workload нет вообще, и эта строка проверяет только файловую политику внутри контейнера.
- **credential_env.** В OpenShell переменная доходит до workload только если раннер передал её через `--env`. Строка показывает выбор раннера, а не работу песочницы.
- **Файлы, которые исполняют снаружи** (`git_hook` … `precommit_config`). В SRT файл остаётся в рабочем каталоге хоста, и `git commit` вне песочницы в control действительно исполнил записанный хук. В OpenShell файл остаётся в контейнере; риск появляется, только если рабочий каталог потом синхронизируют на хост или в CI, а это не испытывалось.

## Что этот прогон не проверяет

Claude Code и managed settings; встроенные инструменты (Read, Edit, WebFetch, WebSearch); хуки, MCP-серверы, `apiKeyHelper` и `statusLine`, которые Claude Code запускает вне песочницы; инъекцию через файл правил; DNS через системный резолвер; настоящий `/var/run/docker.sock`; фильтры содержимого (`filterRequest`/`tlsTerminate` у SRT, правила запросов в `network_policies` OpenShell); OpenShell без network rules; аутентификацию шлюза и providers. Перечень с причинами — в [README](../../README.md#что-не-покрыто).
